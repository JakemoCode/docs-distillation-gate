# Findings from the first real install, 2026-09-18

Status, 2026-09-21: findings 1, 2 and 3 are fixed in #2. Findings 4 and 5 are
open, along with both notes at the end. The fix for 2 is not the one suggested
below; see the note under that finding.

Installed the gate into `career-context`, a repo with 173 existing markdown
files, and ran it against a branch that **distilled documents already on the
trunk** rather than drafting new ones. Nine of the ten gated documents ended up
needing a `Doc-distill-override:` trailer, which is the gate being bypassed on
its first use, so the shape of that failure seemed worth writing down.

Every finding below was reproduced against `8d5fabd` before it was written here.
Line numbers are from that commit.

---

## 1. Code added inside an existing fence is billed as prose

`countWords` starts with `fenced = false` and flips it on each fence line it
sees. For `kind === 'new'` it reads a whole blob, so the opening fence is always
present. For `kind === 'edit'` it reads `addedLines(...)`, which is a diff slice.
Lines added **inside** a fenced block that already exists on the trunk never see
their opening fence, so the counter treats them as prose.

```js
proseWords('const alpha = beta;\nreturn gamma delta epsilon zeta;')
// 8   (hidden: 0)
```

Adding two lines to an existing shell block reads as eight prose words the
document then has to halve. The effect is largest on runbooks, which are mostly
fenced commands.

**Suggested fix.** Seed the fence state for an edit slice by asking whether the
first added line's position in the blob is already inside a fence, or count
prose for edits against the blob and take the diff only to decide *which* lines
are chargeable.

## 2. `fencesBalance` runs on the diff slice, so balanced documents report as unclosed

Same root cause, different symptom, and this one blocks rather than inflates.

```js
fencesBalance('```')              // false
fencesBalance('```sh\ncmd\n```')  // true
```

When an edit replaces a fenced block but leaves the closing fence untouched, the
added-lines slice holds one opening fence and no closer. The document is fine;
the slice is not.

Observed on `context-docs/SCAN-RUNBOOK.md`: eight fences, four pairs, and the
gate refused to count it. The diff carried one `+```sh` whose partner was an
unchanged context line, because the block being replaced ended with the same
bare ` ``` ` as the block replacing it.

**Suggested fix.** Measure `fencesBalance` against `blobAt(repoDir, sha, name)`
rather than the added-lines text. The check is a statement about the document,
not about the edit.

**Not what shipped.** Moving the check alone severs it from the counter, which
still reads the slice. Retag a block's opener, append prose past the unchanged
closer, and the slice carries one fence: every line after it counts as hidden,
200 words measure as 0, and the document passes at exit 0 with no output. The
refusal this finding calls a false positive was the only thing catching that.
The counter had to move with the check, so #2 fixed this with finding 1 rather
than on its own.

## 3. An override cannot clear an unbalanced-fence report

`check-docs.mjs:653`

```js
      `${path} has an unclosed fenced block, so its prose cannot be counted.`,
      '  Close the fence. One stray ``` makes every line after it free.',
    );
    failed = true;
  }
```

No `if (overridden.has(path)) continue;`, unlike the blocks loop at line 667.

Combined with finding 2, a branch that trips the false positive cannot be pushed
at all. An override naming the file is reported as "used with no block behind
it" and printed loudly as a skipped distillation, while the push still fails.
`--no-verify` plus a red CI job is the only way out, which is the outcome the
override mechanism exists to prevent.

**Suggested fix.** Either let an override clear it, or fix finding 2 so the
false positive stops happening. Fixing 2 is better; a genuinely unbalanced
document should still be unpushable.

## 4. `stampMatches` is computed and never read

`check-docs.mjs:615`

```js

```

One occurrence in the file. The staleness branch below it uses `block.stamped`
instead. It reads like an intended check that was never connected.

## 5. Renames made by a merge commit are invisible

`nameHistory` walks commits with `git show --name-status`, which emits no diff
for a merge commit by default.

```
git show -M --name-status --format= <merge>                          ->  0 lines
git show -M --name-status --format= --diff-merges=first-parent <m>   ->  6 lines
```

A branch that renames a gated document inside a merge from the trunk loses the
rename, so the document is re-measured as a fresh draft against its new name and
its curve starts over.

**Suggested fix.** `--diff-merges=first-parent` on that `git show`.

## The thing underneath findings 1 to 3

The gate assumes a branch **drafts** a document: added lines are the draft, and
halving them is halving the work. That assumption is load-bearing in three
places and it inverts for a distillation branch, where every reworded line is an
"addition" and the slice is an artefact of the diff rather than a unit of text.

Measured on the install branch: nine documents went 23,644 prose words to
15,705 against the trunk, 66.4%, with two of them under 55%. The gate saw
none of that, because it was comparing each document's added lines against
themselves.

Two ways out, and the second is probably better:

- **Detect the shape.** When a document's prose count *against the trunk blob*
  has fallen, measure the curve that way instead of on the slice.
- **Say it is out of scope.** The gate is a guard against new verbose documents,
  which is a coherent and useful thing to be. A one-line note in the README that
  retroactive distillation of an existing corpus is not what it measures would
  have saved the confusion entirely, and the nine overrides with it.

## Smaller note: the ignore list wants document *kinds*, not paths

Three categories in `career-context` are structurally undistillable and each
needed its own ignore entry:

- **Registers**, which grow by design. An enforcement ledger gaining a row per
  rule, a backlog, a status log. The README already names this case.
- **Decision records.** Their own convention requires keeping "reasoning that
  later turns out wrong, because a rule whose rationale has expired is the
  hardest kind to spot", which is the exact opposite of removing restated
  context. Thirteen ADRs, 11,957 words.
- **Verbatim pasted text**, where editing falsifies a record. Cover letters
  actually sent, a prompt kept word for word.

Nothing generalises these, so every repo rediscovers them one blocked push at a
time. Worth a paragraph in the README naming the three, even without a code
change.
